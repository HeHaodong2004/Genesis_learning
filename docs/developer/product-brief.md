# 贯穿项目：Genesis Experiment Hub

这是可选的全栈交付支线，不是机器人学习主线，也不是已经部署完成的服务。先完成物理、观测、GAE和辨识练习；只有需要把研究工具提供给其他用户时，再进入本计划。

## 谁使用，解决什么

首位用户是你自己，第二位用户是愿意查看你实验结果的同学。当前任务是：给定一次已完成实验，在两分钟内知道用了哪份配置、哪版代码、哪些指标、缺了什么产物，能将两次兼容实验放在一起解释。先测量一次现在手工完成任务的时间，才能判断产品有没有帮助。

第一版只读已完成实验；实验启动、GPU 调度、多租户、付费与在线控制机器人留到后续有真实需求时。这样第一条产品链路足够小：**导入一份固定示例 → 列表 → 详情 → 缺文件错误提示 → 测试 → 部署到个人测试环境**。

## 技术决策草案

| 层 | 起点 | 验收重点 |
| --- | --- | --- |
| 领域逻辑 | 当前工作台的配置与产物检查概念 | 能用小数据离线测试；不依赖 Web 框架 |
| API | Python / FastAPI / Pydantic | 公开 schema、稳定错误、拒绝无效输入 |
| 存储 | SQLite 元数据，原始产物仍为文件 | 迁移可重放，配置摘要与代码版本可追踪 |
| 前端 | TypeScript / React | 加载、空数据、错误、正常四种状态可演示 |
| 构建与交付 | 一套锁定依赖、测试、CI、容器 | 在干净环境重建；保留上一版回退路径 |
| AI 能力（后加） | 依据实验数据生成带来源的摘要 | 固定评估集，能发现编造与缺证据回答 |

这是适合这一学习项目的选择，不意味着行业只有这一套栈。开始每一阶段时以对应官方文档与实际版本校准 API，不直接照搬一份三年不变的版本清单。先保持科学环境稳定，将产品依赖放入独立环境，避免用 Web 库升级牵动 CUDA/Torch。

## 先写 API 契约，再做 UI

下面是可评审的 **设计示例，当前尚未实现**：

```text
GET /api/health
200 {"status":"ok"}

GET /api/runs
200 {"items":[{"id":"demo-eval-001","name":"demo","status":"complete"}]}

GET /api/runs/demo-eval-001
200 {"id":"demo-eval-001","config_digest":"...","git_commit":"...",
     "metrics":{},"warnings":[]}

GET /api/runs/not-found
404 {"error":{"code":"RUN_NOT_FOUND","message":"Run not found"}}
```

URL 使用服务内部的 run ID，不接受任意服务器文件路径。不要把整个 home 目录或研究仓库做成静态目录公开。示例数据使用 synthetic fixture；真实数据是否可分享是独立的产品决策。生产 API 返回用户需要的字段，主机名、命令行、绝对路径等 provenance 内部信息默认保留在服务端。

## 五个可交付的小任务

每项都能单独做成 PR，避免一次同时学习十个系统。

1. **只读 API**：写一个完整和一个缺文件 fixture；用请求测试验证 200、404、错误 schema。验收：不启动 Genesis，任何 GET 不修改原数据。
2. **元数据存储**：设计 `runs` 表和唯一 ID；重复导入必须有明确策略；用临时数据库测迁移与重复输入。验收：重启服务仍能读取同一 run。
3. **前端纵向切片**：列表点击进入详情；做 loading/empty/error/success 状态；后端断开时给可理解错误。验收：另一个人只读界面即可说明当前结果可信范围。
4. **协作和交付**：一位同学按 README 在干净环境运行；CI 在坏请求测试失败时阻止合并。验收：记录一次真实使用反馈和改动，部署记录包含版本与回退步骤。
5. **AI 摘要（可选后期）**：答案附引用字段；不把缺失值补成确定结论；对不兼容实验拒绝直接排名。验收：固定十个例子包含缺数据、冲突和不可比较输入，记录失败类型、延迟、成本。

## “产品做好了”的证明

保留一个短演示、一页架构图、一份 API 契约、一组测试、一个真实用户反馈、一次故障复盘。面试时用这些讲清楚你做过的取舍。代码量、框架数量和 AI 生成字数不能替代这些证据。
